# 求职表述、演示与面试问答

本文件只把仓库已经支持的事实组织成求职表达，不创造新的职责、数据或成果。技术细节
以[架构](architecture.md)和[数据与评估](data-and-evaluation.md)为准。

## 1. 推荐定位

项目可以定位为：

> 一个基于半合成数据、强调评估完整性和离线/在线一致性的岗位推荐与能力评估原型。
> 它展示了 LightGCN、文本和技能证据的多路推荐，类型化技能路径，版本化模型发布，
> 可解释排序，以及带鉴权和反馈持久化的 FastAPI 服务。

不要把它定位为“真实招聘平台”“生产上线系统”或“证明提升业务指标的项目”。原始
真实数据已经丢失是必须主动说明的限制，而不是等面试官追问后才承认。

## 2. 60 秒项目介绍

> 我维护了一个岗位推荐与能力评估原型。原项目的真实数据已经丢失，所以我没有复述
> 无法验证的历史效果，而是用固定种子半合成数据重建了可复现的工程证据。离线侧用
> 逐用户留出、训练图隔离、合法 BPR 负采样和 seen masking 防止泄漏，比较随机、
> 流行度、技能、文本、LightGCN 和融合模型；结果显示技能基线反而最好，我保留了这
> 个负面结论。工程侧用版本化 ModelBundle 统一训练和服务映射，显式区分已知用户和
> 冷启动路径，排序解释与最终分数严格可加。能力评估只使用带来源的先修边，LLM 输出
> 必须过 schema，失败则确定性兜底。最后通过 FastAPI、曝光后反馈、SQLite 持久化、
> 鉴权和自动化测试把链路闭环；姓名、手机、邮箱和通讯地址在进入 SQLite 前逐字段
> AES-GCM 加密，只有本人或管理员可解密。这个项目证明的是设计和实现能力，不是真实
> 用户效果或法规合规。

这段话包含四个面试抓手：数据诚信、推荐协议、离线/在线一致性、可靠服务边界。

## 3. 简历项目描述模板

先根据自己的真实参与方式补全 `[独立完成/负责/参与]`，不要虚构 Team Lead、团队
人数或日期。

**JobRec-KG｜Python、PyTorch、FastAPI、Pydantic、SQLite、Neo4j（可选）**

- `[独立完成/负责]` 岗位推荐与能力评估原型，组合 LightGCN、离线文本召回与技能
  覆盖；为已知用户和冷启动用户设计可观察的不同召回路径。
- 建立逐用户留出、训练图隔离、未观察 BPR 负采样和训练期岗位屏蔽规则，并用构造式
  测试保护数据泄漏边界；五种子实验保留复杂模型未超过技能基线的负面结果。
- 设计版本化 `ModelBundle` 统一 checkpoint、ID 映射、seen set 和排序权重；实现
  请求级无状态归一化，使响应中的因子贡献可与最终分数核对。
- 使用类型化技能先修边和 Pydantic 约束能力建议；外部图/LLM 可替换且有确定性兜底，
  FastAPI 服务包含演示鉴权、唯一曝光归因、SQLite/WAL 持久化和自动化质量门禁。
- 实现 Persona 约束的合成用户评估：用 Pydantic 校验可选 LLM 的结构化人岗判断，
  再以位置观察概率模拟点击/收藏/投递；固定种子测试覆盖非法输出降级和 seen 屏蔽。
- 对赛题要求的姓名、手机、邮箱、通讯地址实施 AES-GCM 字段加密与上下文绑定；使用
  本人/admin RBAC、独立角色凭据和构造式测试验证越权、篡改及密文调换拒绝。
- 为缺失真实数据设计隔离的外部数据 staging：通过官方 API 获取公开岗位，使用
  Pydantic 校验、HMAC 用户 ID 伪名化和带输入哈希的 manifest；未把导入误写成效果。

如果投递推荐/生成式推荐岗位，可用第五条替换安全或外部数据条目；不要把确定性基线
的 12.0% 写成 LLM 或真人效果。安全/后端岗位保留隐私条目，数据工程岗位保留 staging
条目。它们比堆叠框架名更能证明工程判断。

## 4. 建议的演示顺序

### 4.1 演示前

```bash
uv sync --frozen --extra dev
uv run python -m pytest -q
uv run uvicorn src.api.routes:app --host 127.0.0.1 --port 8000
```

准备两个输入：

- 已知用户 `user_001`，展示非零 LightGCN 贡献、模型版本和已知用户模式；
- 新用户简历文本，例如 `Python SQL Docker machine learning`，展示冷启动模式。

### 4.2 五分钟主线

1. 打开 `/demo` 或 `/docs`，先说明所有展示数据为半合成数据。
2. 调用已知用户推荐，指出 `request_id`、`impression_id`、`retrieval_mode`、
   `model_version` 和三项贡献。
3. 调用冷启动推荐，说明为什么没有可用的协同历史。
4. 对明确 `job_id` 做能力评估，展示技能 gap、类型化路径边证据和兜底建议。
5. 保存四项个人字段，展示本人可读、招聘方不可读和 SQLite 中只有密文，再删除档案。
6. 携带实际返回的 `impression_id` 提交 feedback，再展示管理汇总；说明错配曝光和
   同一曝光重复反馈都会被拒绝。
7. 打开 `results/experiment_summary.json`，主动指出技能基线最好，而不是只展示融合模型。

### 4.3 十分钟代码阅读路线

```text

src/data/external.py           外部数据契约、伪名化与 lineage
src/data/private_profile_store.py  四字段加密存储与 AAD 绑定
src/utils/training.py          BPR 负采样、训练和离线指标
src/models/bundle.py           离线/在线发布契约
src/api/routes.py              known/cold 编排、能力评估、反馈边界
src/ranking/linear_fusion.py   请求级归一化与贡献解释
src/data/graph_store.py        内存/Neo4j 证据适配器
src/generation/adapters.py     schema 校验和确定性兜底
src/simulation/                Persona 判断、位置偏置行为与离线汇总
tests/                         防泄漏、排序、安全、持久化和 API 契约
```

## 5. 高频追问与回答要点

### Q1：真实数据丢失后，这个实验还有价值吗？

有，但价值发生了变化。半合成数据不能证明业务效果，只能证明实现、数据协议和模块
契约可运行。我把实验目标从“复现历史效果”改成“防止泄漏、比较相同协议下的基线、
打通离线发布与在线服务”。若要判断真实效果，必须重新取得合法新数据并重做时间切分、
标签和线上验证。

### Q2：为什么不声称旧项目的 23k 节点、168k 边或 80% 有效率？

因为原始数据、运行日志和评估协议都不存在，无法审计。旧数字最多是历史未验证说法
或赛题目标，不是当前成果。面试中可说明材料背景，但不能把它当实测证据。

### Q3：为什么还保留 LightGCN，明明技能基线更好？

LightGCN 用于展示协同召回、图构造、BPR 和模型发布链路；实验结论则诚实说明它在
当前小型、技能驱动、半合成分布上没有优势。真实产品是否保留它，需要用真实时间序列
交互、冷启动分层和显著性分析重新判断，而不是由框架复杂度决定。

### Q3.1：没有原始数据，准备怎样获取新数据？

把数据拆成四类处理：ESCO/O*NET 提供职业与技能本体，USAJOBS 官方 API 提供公开岗位
快照，交互只使用仍获许可的学术数据或自己取得明确同意的事件。仓库已经实现本地
staging、schema 校验、用户 ID 伪名化和 manifest，但没有自动接入训练。原因是这些
来源许可证和实体空间不同，必须先完成技能映射、时效/去重、时间切分与 bundle lineage，
再谈真实数据实验。不会抓取公开个人主页来补简历。

### Q4：怎么避免离线评估泄漏？

先逐用户切分，再只用 `train_R` 构图和训练；负样本排除用户已观察岗位；评估时把
所有训练期岗位设为不可选；服务 bundle 同样保存 train seen set。测试专门构造一个
若 seen item 未屏蔽就会失败的场景。

### Q5：为什么用线性排序而不是 DeepFM 或学习排序？

当前数据量和标签来源不足以支持复杂模型收益结论。线性排序便于离线/在线统一，归一化
可以做到请求无状态，且每个因子贡献与分数严格对应。如果未来有足够真实曝光/结果日志，
可以在同一候选和时间切分协议下比较 LTR，而不是先换框架再找理由。

### Q6：GAT 学到了什么？

它根据技能图结构和岗位关联特征训练一个静态技能权重表，发布到 bundle 后在线只查表。
训练监督是代理信号，所以它展示的是图特征和发布方法，不是真实市场技能重要度。实验
中 E3 对 E2 的均值优势很小，也不足以声称稳定提升。

### Q7：为什么说解释可信？

排序对当前候选集生成同一个归一化特征矩阵，最终分数是各列乘权重之和，响应贡献也
从该矩阵逐列计算。测试验证调用顺序不改变结果，并验证贡献和等于分数。它是模型内
因子解释，不代表因果解释。

### Q8：Neo4j 是真正接入还是 PPT 架构？

仓库有真实 driver 适配器、Cypher 和幂等导入脚本，已知用户能力请求会调用当前配置
的图适配器，并报告实际来源。但保留环境没有外部 Neo4j 集成证据，所以状态是“已实现、
环境受限”，不能说验证了稳定性和性能。

### Q9：LLM 失败怎么办？

LLM 只负责把已有差距和图路径组织成结构化建议。输出必须符合 `CareerAdvice` schema；
网络错误、非法 JSON 或字段越界都会进入确定性 fallback。这样模型失败不会破坏接口，
但 fallback 的内容质量同样只是演示，没有专家评估。

### Q10：反馈闭环是否真的训练模型？

目前只持久化曝光和满意/不满意反馈并提供统计，未自动增量训练。每个推荐结果带唯一
`impression_id`，反馈必须与该曝光的用户、岗位、模型版本一致，同一曝光只能记录一次。
这解决了演示中的基础归因，但真正闭环仍需要实验分组、事件时钟、延迟标签、训练快照、
离线审批、灰度和回滚，不能由一个比例接口代替。

### Q10.1：为什么用 LLM 模拟用户，这能替代真实用户吗？

不能替代。我的实现把 LLM 限定为潜在人岗相关性的代理判断，输入不含 rank、推荐分数
和 80% 目标，`effective` 由固定代码派生；随后由独立的位置观察概率模型生成点击等
合成行为。这样可以离线测试 prompt、schema、失败降级和行为假设，但模型偏好、提示词
敏感性与 realism gap 仍存在。当前只保留确定性基线实测，外部 LLM 路径是已实现、
环境受限；真正报告 `LLMProxyEffectiveness` 前还要固定模型版本并与盲测人工样本校准。

### Q10.2：赛题 Data Privacy 要求完成了吗？

赛题明确要求保护简历隐私，并对数据库里的姓名、手机、邮箱、通讯地址等至少四项加密，
只能由授权人员解密。当前演示路径已完成：简历请求不落库，四项档案在写 SQLite 前用
AES-GCM 加密，AAD 绑定用户和字段；只有本人或 admin 可读写删除，其他用户和 recruiter
被拒绝。测试还会直接搜索数据库明文并调换合法密文验证认证失败。这个结论只覆盖赛题
功能条款，不代表 GDPR/PIPL、生产安全审计或完整数据生命周期合规。

### Q11：开发中最有代表性的问题是什么？

优先选择与岗位匹配的案例，不要一次罗列全部修复。推荐系统岗位可讲训练期岗位未屏蔽
导致 Recall 失真的最小反例；后端岗位可讲反馈从“存在任意历史曝光”收紧到唯一
`impression_id`，并用事务和唯一索引拒绝重复；平台岗位可讲请求内训练改为
`ModelBundle` 离线发布；数据工程岗位可讲外部数据从“可下载”拆为许可核对、隔离
staging、伪名化和显式训练接入。每个案例都按“风险—假设—反例—取舍—测试—边界”回答，
完整证据卡见[开发问题与解决方案](problem-solving.md)。

### Q12：项目离生产还有多远？

差距包括合法真实数据、简历解析、岗位 feed、身份/KMS、事件平台、模型注册、
多 worker/耐久/故障测试、漂移与偏差治理、线上实验和成本评估。当前优势是这些边界
被显式设计和测试了一部分，而不是已经完成生产化。

## 7. 面试后的改进优先级

在真实数据前提不变时，优先提升可证明的工程质量，而不是继续叠加模型：

1. 增加核心 API、图适配器和实验 runner 的构造式覆盖；
2. 为 bundle 增加哈希、代码版本和数据生成配置 lineage；
3. 为反馈事件增加实验分组、有效期和客户端事件 ID，完善迟到、撤回和重放语义；
4. 完成 ESCO/O*NET 技能映射和外部 snapshot 到 bundle 的显式 lineage，再按许可做
   独立实验；
5. 只有在新的合法真实数据与明确业务目标出现后，再讨论领域微调、LTR、在线实验和
   公平性审计。
