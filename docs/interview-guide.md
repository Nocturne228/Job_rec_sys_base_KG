# 面试讲解与简历边界

## 1. 一分钟版本

我把原来的静态岗位匹配原型改造成了自包含的岗位内容流推荐系统。数据层生成带时间、
位置、点击、停留、收藏和投递的曝光日志，并按用户时间留出。召回层使用 LightGCN、
文本、技能和热度/新鲜度四路 Top-K，合并时保留来源；排序层从训练曝光学习协同、内容、
近期兴趣等六项特征，最后用确定性重排平衡相关性、多样性和新岗位探索。离线模型通过
覆盖完整 Serving 配置的哈希发布，API 返回候选来源和可加贡献。外部 LLM 只做带输入
证据的兴趣/query 扩展，失败时确定性降级。

## 2. 推荐演示顺序

1. `GET /api/model`：说明数据、协同权重和完整 Serving 行为如何版本化；
2. 已知用户推荐：观察 `lightgcn` 来源、近期兴趣特征和 seen masking；
3. 冷启动简历：观察文本/技能/新鲜度召回，没有伪造协同历史；
4. `recall_sources`：解释候选为什么进入排序，而不只解释最终分数；
5. `contributions`：核对 Pointwise logit、截距和重排调整之和；
6. 提交点击/停留/收藏或满意度反馈，再次提交同一曝光应返回冲突；
7. 展示五种子负面结果：Fusion 优于 Pointwise，多阶段候选 Recall 只有 0.7109。

## 3. 与主 Feed 推荐岗位的对应关系

| 岗位能力 | 当前可展示证据 | 明确边界 |
|---|---|---|
| 召回 | 四路 Top-K、合并去重、来源/排名、候选 Recall | 精确小目录，没有 ANN 实测 |
| 排序 | 训练曝光、六特征 Pointwise、可加 logit | 不是 DIN/MMoE，且负面结果 |
| 兴趣建模 | LightGCN 长期兴趣 + 最近五条岗位技能兴趣 | 没有严格逐曝光时点回放 |
| 流量分发 | 技能多样性、新岗位奖励、Coverage/Fresh Share | 不代表真实生态或商业策略 |
| 生成式推荐 | 证据受限结构化兴趣/query、Schema、fallback | 默认没有外部 LLM 实测 |
| 工程一致性 | Bundle v3、Serving 哈希、lifespan、曝光归因 | 单机 SQLite，不是生产平台 |

岗位推荐与短视频的共同点是候选生成、排序、短长期兴趣和流量约束；差异是岗位反馈低频、
技能约束强、用户目标更稳定，投递也不能等价于观看时长。面试中应主动说出差异。

## 4. 推荐系统追问

### 为什么保留固定融合，而上线用 Pointwise？

固定融合是重要基线，当前实测甚至更好。Pointwise 的价值是展示如何从曝光而不是只从
正反馈学习、如何做离线/在线共享特征和模型发布。若做真实决策，我会在得到时间回放、
更多曝光和验证集后再决定是否替换简单模型，而不会因复杂度直接上线。

### 为什么 Candidate Recall 只有 0.7109？

四路各取 Top-20 是人为设置的计算预算，去重后候选无法覆盖全部目录。该结果暴露了候选
阶段的损失，说明召回和精排必须分阶段评估。可调大 K、增加语义双塔、训练召回模型，
但要同时报告延迟、内存和候选规模。

### 为什么不用 FAISS？

当前只有 50–100 个岗位，精确 Top-K 更容易复核且不会引入近似误差。候选协议已经与
索引实现分离；达到十万级并确认精确计算成为瓶颈后，再以精确结果为基准验收 ANN Recall
和延迟。

### Pointwise 为什么输了？

每个种子只有约 1.5k 训练曝光、约 10% 正例，特征又是训练窗口末端静态快照。Logistic
容易把生成分布中的协同/近期兴趣相关性学得过强，而技能先验已经直接接近 oracle 机制。
这是数据和协议诊断，不是“学习排序无效”的结论。

### LLM 如何避免幻觉？

LLM 不能创建用户未表达的技能。每个兴趣和扩展 query 都必须带输入证据，Pydantic
验证不通过就丢弃全部生成结果并使用确定性词项提取。生成结果只是召回 query，不替代
结构化技能差距。当前没有外部模型实测，所以只说适配器已实现、效果环境受限。

### 流量重排是不是公平性？

不是。当前只对内容相似度和发布时间做确定性调整，指标是列表多样性和新岗位占比；没有
受保护属性、治理目的或真实结果，不能称公平性或生态健康认证。

## 5. 可用于简历的表述

> 设计岗位内容流多阶段推荐原型：基于时间化曝光日志构建 LightGCN、文本、技能及
> 热度/新鲜度四路召回，保留候选来源并使用六特征 Pointwise 模型排序；通过可加分数
> 解释和 Serving 内容哈希保证离线—在线一致。

> 增加近期行为兴趣与多样性/新岗位重排，统一评估 Recall、NDCG、候选覆盖、列表多样性
> 和新岗位占比；五种子实验中固定融合 Recall@10 为 0.2551，高于 Pointwise 的 0.1410，
> 保留负面结果并定位半合成曝光量、正例稀疏和静态特征限制。

> 实现证据受限的可选 LLM 兴趣与 query 扩展：结构化输出要求逐项输入证据，外部调用
> 超时或 Schema 不合法时确定性降级；当前无外部模型实测，不宣称生成式推荐提升。

不要写“抖音同款”“CTR 提升”“百万级实时推荐”“生成推荐效果提升”或“线上流量优化”。

## 6. 后续最有价值的改进

1. 对每条历史曝光做 point-in-time 特征回放；
2. 将 Hashing 基线升级为固定版本双塔，并验证 ANN；
3. 获得更长序列后比较时间衰减、DIN-style 注意力和 Transformer；
4. 标签量和业务目标明确后做点击/收藏/投递多任务；
5. 固定外部模型、缓存和人工证据协议后运行 LLM 消融。
