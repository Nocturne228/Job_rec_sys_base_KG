# 开发问题与解决方案

本文件记录已经关闭、且能体现工程判断的问题。它面向开发复盘和面试追问，不是
Changelog、待办清单或第二份架构文档。当前系统行为见
[架构说明](architecture.md)，数据协议与实测数字见
[数据与评估](data-and-evaluation.md)。

## 1. 面试使用方法

回答问题时不要背诵实现清单。建议按下面的顺序在 60～90 秒内讲清一个案例：

1. **现象和风险**：什么行为不可信，会影响哪一个结论；
2. **约束和假设**：先明确必须保护的不变量，再列出可能原因；
3. **定位证据**：沿哪条数据流或调用链排除假设，最小反例是什么；
4. **方案和取舍**：为什么选择当前方案，没有选择的方案缺什么前提；
5. **回归和边界**：哪个测试会在问题复发时失败，还有什么不能由当前仓库证明。

面试官继续追问时，优先打开对应测试展示“失败条件”，再回到代码。只展示正常输出
通常只能证明系统跑过，构造式反例才能证明边界受到保护。

## 3. 已关闭问题记录

### P-001：半合成结果容易被误写为真实业务结论

**问题与影响**：原始真实数据已经丢失，旧材料同时存在赛题目标、历史规模和生产化
表述。如果继续复述，半合成协议上的离线指标会被误解为真实用户效果、业务提升或
上线能力。这不是文案问题，而是证据链断裂。

**分析思路**：先停止从旧总结反推事实，按“代码/测试 → 版本化产物 → 评估协议 →
摘要文档 → 外部资料”的顺序重建证据。对每个数字追问四件事：数据在哪里、协议是
什么、何时运行、机器可读结果在哪里。缺少任一项，就不能标为当前已验证成果。

**解决办法与取舍**：使用固定种子生成透明的半合成分布，目标从“恢复历史效果”改为
验证代码路径、接口契约和评估协议；建立证据标签，并把易变数字集中到
[数据与评估](data-and-evaluation.md)。没有选择伪造一份“接近旧规模”的数据，因为
扩大合成规模不会恢复真实标签、选择偏差或用户语义。

**回归证据**：生成可复现性和信号透明性由
[`test_mock_generation_and_per_user_holdout_are_reproducible`](../tests/test_core_pipeline.py)
与 [`test_generated_behavior_is_compatibility_conditioned`](../tests/test_data_graph_and_ranking.py)
约束；机器可读实验结果位于
[`results/experiment_summary.json`](../results/experiment_summary.json)。

**遗留边界**：没有新的合法数据，就不能补足真实满意度、投递、面试、公平性或生产
规模结论。面试时应主动说明，而不是等到被追问后才披露。

### P-002：切分、负采样和评估屏蔽的局部正确仍可能造成污染

**问题与影响**：早期实现虽使用 `train_R` 构图，但全局随机切分可能让某个用户没有
训练交互；BPR 负样本直接随机抽岗位，可能抽到该用户已观察的正例；评估又没有屏蔽
训练期岗位。三处任一失守都会让指标含义失真，单看最终 Recall 波动无法定位。

**分析思路**：把训练图、正负样本和候选屏蔽拆成三个独立不变量，不把“已经切分”
当成“没有泄漏”。为评估构造一个用户、三个岗位的反例：训练岗位分数最高、测试岗位
次高；如果没有 seen masking，Recall@1 必须失败。负采样则直接检查抽中位置在
`train_R` 中是否为零。

**解决办法与取舍**：改为固定种子的逐用户留出，保证评估用户至少有一个训练交互和
一个测试正例；BPR 只从未观察岗位采样，无合法负样本的用户退出该批次；离线评估和
服务 bundle 都屏蔽训练期已见岗位。当前没有改为时间切分，因为半合成事件缺少可代表
真实反馈延迟的时间语义，伪造时间窗口只会制造另一层不实假设。

**回归证据**：[`test_mock_generation_and_per_user_holdout_are_reproducible`](../tests/test_core_pipeline.py)、
[`test_heldout_evaluation_masks_training_interactions`](../tests/test_core_pipeline.py) 和
[`test_negative_sampler_never_selects_observed_item`](../tests/test_security_persistence_and_statistics.py)
分别保护切分、评估屏蔽和负采样边界。

**遗留边界**：逐用户随机留出只能验证当前协议；真实上线评估仍需要事件时间、岗位
有效期、反馈延迟、候选池快照和冷启动分层。

### P-003：请求内重建模型让“同一模型版本”失去含义

**问题与影响**：早期 API 首次请求时在进程内初始化并训练 GAT，推荐响应还混入固定
占位贡献。不同进程可能得到不同状态，请求延迟包含训练开销，离线评估的映射和在线
映射也无法核对。即使接口返回 200，也不能证明服务的是已评估模型。

**分析思路**：沿“数据种子 → ID 映射 → checkpoint → seen set → 排序权重 → API
响应”核对 lineage。发现服务没有一个能同时约束这些状态的发布单元，因此根因不是
缓存慢，而是缺少离线/在线契约。

**解决办法与取舍**：引入经 Pydantic 校验的 `ModelBundle`，把 checkpoint、连续 ID
映射、训练期已见集合、技能权重和排序权重作为一个版本发布；FastAPI 在 lifespan 中
一次加载并校验，损坏或映射不一致时启动失败。没有采用“缺 bundle 就自动重训”的
降级，因为它会把部署错误伪装成成功并产生不可追溯模型。

**回归证据**：[`test_authenticated_api_known_cold_start_competency_and_feedback`](../tests/test_api_contract.py)
通过真实 lifespan 加载 bundle，并验证已知用户路径、冷启动路径和模型贡献；发布契约
实现位于 [`src/models/bundle.py`](../src/models/bundle.py)。

**遗留边界**：当前 bundle 尚无 checkpoint 哈希、代码版本和完整数据配置 lineage，
也没有模型注册、审批、灰度和回滚系统。

### P-004：首次请求的归一化统计污染后续排序

**问题与影响**：早期排序器会缓存第一次候选集的 min/max，后续请求复用该统计。
同一组候选可能因之前处理过另一组极端分数而改变排序；解释若从原始值或另一套归一化
计算，也无法与最终分数相加核对。

**分析思路**：不要只测单次排序。先对固定候选求结果，中间插入一组数值范围完全
不同的候选，再对原候选求一次；如果前后不同，就说明请求间存在隐藏状态。随后逐项
核对 `score == sum(contributions)`，把稳定性和可加性分开验证。

**解决办法与取舍**：归一化限定在本次候选矩阵内，不保存跨请求拟合状态；最终分数
和解释贡献使用同一个归一化矩阵与权重。没有使用全局离线统计，是因为当前 bundle
尚未发布经训练数据拟合、带版本的统计量；无版本的“全局统计”仍会造成离线/在线偏差。

**回归证据**：
[`test_query_normalization_is_stateless_and_explanations_are_additive`](../tests/test_data_graph_and_ranking.py)
同时构造调用顺序反例并验证贡献可加。

**遗留边界**：请求级 Min-Max 使分数只适合当前候选内比较，不应跨请求解释绝对分值；
未来若发布全局校准器，必须把统计量版本纳入 bundle。

### P-005：图证据来源标签与实际查询路径不一致

**问题与影响**：配置 Neo4j 后，能力评估曾继续走内存 `GraphLoader`，却把响应的
`evidence_source` 标成 Neo4j。展示看起来接入了外部图，实际证据并未经过该适配器，
属于可追溯性错误。

**分析思路**：沿 `POST /api/competency` 调用链同时追踪“路径数据从哪里来”和“来源
标签在哪里赋值”，不能只检查 driver 类是否存在。再区分两类输入：已知用户可由持久
图查询；临时简历覆盖输入并不存在于外部图中。

**解决办法与取舍**：已知用户且没有请求文本覆盖时调用当前配置的
`SkillGraphStore.competency_evidence()`；临时简历输入明确使用内存类型边，并返回
`typed_in_memory_graph`。没有把临时简历静默写入 Neo4j，因为请求处理器不应产生训练
或画像侧状态变更，也缺少个人数据治理依据。

**回归证据**：[`test_authenticated_api_known_cold_start_competency_and_feedback`](../tests/test_api_contract.py)
注入 stub graph store，验证实际路径内容和 `evidence_source` 同时改变；类型化边的方向、
来源和置信度由 [`test_typed_graph_path_contains_edge_provenance`](../tests/test_data_graph_and_ranking.py)
约束。

**遗留边界**：Neo4j driver、Cypher 和导入脚本状态为已实现，但当前环境没有外部服务
集成、故障恢复或性能证据。

### P-006：仅按用户和岗位关联反馈会重复计数或错配历史曝光

**问题与影响**：第一版持久化修复只要求同一用户、岗位和模型版本存在任意曝光。
同一岗位多次出现时无法判断反馈对应哪一次展示，同一个曝光也可以重复提交，导致
`effectiveness` 的分母和分子被重复事件污染。

**分析思路**：从指标反向检查事件最小主键，而不是只看是否存在 `impression` 行。
构造三类反例：不存在的曝光 ID、曝光 ID 与岗位不一致、同一曝光第二次反馈。三者都
必须被拒绝，才能把一次反馈归因到一次实际展示。

**解决办法与取舍**：推荐请求生成 `request_id`，每个结果写入曝光后返回唯一
`impression_id`；反馈必须携带该 ID，并与用户、岗位、模型版本逐项匹配。SQLite 使用
部分唯一索引保证一个曝光最多一个反馈，写入前用 `BEGIN IMMEDIATE` 串行化检查与插入；
启动时自动迁移旧事件表，无法精确归因的旧 feedback 行保留供检查但不再进入统计。
没有按“最后一次同岗位曝光”猜测归因，因为多标签页、重试和并发请求下该规则不确定。

**回归证据**：[`test_event_store_persists_feedback_across_instances`](../tests/test_security_persistence_and_statistics.py)
验证精确关联、错配拒绝、重复拒绝和跨实例统计；
[`test_event_store_migrates_legacy_schema_before_exact_feedback`](../tests/test_security_persistence_and_statistics.py)
验证旧 schema 迁移；API 契约测试验证 `request_id`、唯一 `impression_id` 和 409 响应。

**遗留边界**：当前还没有实验分组、客户端事件 ID、曝光有效期、迟到/撤回规则与消息
队列幂等消费，因此统计仍是本机演示诊断，不是线上因果效果。

### P-007：外部 LLM 的成功响应不等于合法业务响应

**问题与影响**：外部模型可能超时、返回非 JSON、遗漏技能 ID 或生成与图证据无关的
路径。如果把字符串直接返回，接口契约和证据边界都会被概率性输出破坏。

**分析思路**：先划分确定性事实与生成文案：技能差距和图路径由本地代码计算，LLM
只能组织这些证据。然后把网络成功、JSON 可解析、schema 合法视为三个独立检查，不用
一个宽泛的“调用成功”代替。

**解决办法与取舍**：外部输出必须经过 `CareerAdvice` Pydantic 校验；异常或非法
schema 返回由同一技能差距构造的确定性 fallback。没有让 LLM 直接查询或改写图事实，
也没有无限重试，因为这会放大延迟、成本和不可控性。

**回归证据**：[`test_generation_fallback_is_schema_valid_and_nonempty`](../tests/test_security_persistence_and_statistics.py)
验证兜底自身满足 schema；
[`test_llm_simulator_only_parses_bulleted_gap_rows`](../tests/test_security_persistence_and_statistics.py)
保护结构化技能解析边界。API 契约测试确认学习路径非空。

**遗留边界**：当前测试证明的是接口可靠性，不是建议正确性；没有职业专家标注、事实
一致性评分、外部模型版本评估或成本/延迟预算。

### P-008：复杂融合模型没有超过简单技能基线

**问题与影响**：多种子实验中，技能基线的均值优于 LightGCN 和最终融合模型。如果
只展示最复杂架构或删除简单基线，会形成选择性报告，也会掩盖生成器主要由技能兼容度
驱动这一事实。

**分析思路**：先确认所有模型共享数据版本、切分、候选池、seen masking、种子和指标，
排除协议不一致；再看分布构造，发现主要可学习信号就是技能覆盖。在小型稀疏交互上，
协同模型缺少超越显式技能规则的信息量，因此结果符合数据机制，不应先归咎于调参。

**解决办法与取舍**：保留随机、流行度、技能、文本、LightGCN 和融合消融的完整结果，
把结论写成“链路已实现，但当前协议不证明复杂模型收益”。没有继续搜索更多种子或参数
直到融合模型领先，因为那会把模型选择偏差包装成改进。

**回归证据**：统一协议由 `uv run python -m scripts.run_experiments` 生成，逐种子值和
配置在 [`results/experiment_summary.json`](../results/experiment_summary.json)；当前
数值、标准差和生成机制解释只在[数据与评估](data-and-evaluation.md)维护。

**遗留边界**：五个半合成种子没有统计显著性，也不能外推真实场景。是否保留复杂
模型，需要合法真实数据上的时间切分、用户分层、成本和显著性共同决定。

### P-009：局部测试通过不能替代服务边界类型检查

**问题与影响**：单元测试和格式检查曾通过，但关键 mypy 门禁仍发现 Neo4j record
可空、图适配器联合类型和 API 结果列表缺少注解。若文档只写“测试通过”，会把未通过
的边界检查隐藏掉；这类问题也容易在换适配器后变成运行时异常。

**分析思路**：按故障影响分层门禁：语法、行为测试、格式、导入排序和边界类型检查
分别运行，不用一个命令的成功代表全部。对类型错误回到真实可空路径和协议接口处理，
不使用无依据的 `Any` 或 `# type: ignore` 消音。

**解决办法与取舍**：处理空 Neo4j record，使用 `SkillGraphStore` 协议约束适配器，
显式标注 API 响应列表；把 API、bundle、图存储、生成、安全、数据模型和事件存储列入
仓库固定 mypy 门禁。没有立即要求全仓 strict mypy，因为历史训练/实验模块仍有较多
动态科学计算接口，直接开启只会产生大量低信噪比整改。

**回归证据**：执行根 [`AGENTS.md`](../AGENTS.md) 的完整质量门禁；精确日期、测试数和
覆盖率由[数据与评估的工程验证](data-and-evaluation.md#81-本地质量门禁)唯一维护。

**遗留边界**：当前类型检查是关键边界子集，覆盖率门槛也只是最低门禁；实验 runner、
GAT 训练、外部适配器和故障分支仍需逐步增加构造式测试。

### P-010：旧根入口形成第二套训练和演示事实源

**问题与影响**：根 `main.py` 曾包含数百行训练、召回、排序、技能关系和生成演示，
同时 `scripts.build_model_bundle`、实验 runner 和 FastAPI 又有各自实现。直接运行旧
入口会覆盖 `models/lightgcn_model.pt`，却不发布匹配的 `ModelBundle`，可能让在线
checkpoint、映射和 seen set 分裂；复制的先修边与排序参数也会随时间偏离规范实现。

**分析思路**：从每个公开入口反向追踪它写入哪些产物、是否共享切分和发布契约，而
不是仅看函数能否运行。入口层若包含领域实现，就必须回答哪一套代码是事实源；无法
回答时，问题是职责重复而非注释不足。

**解决办法与取舍**：删除旧演示实现，把根入口收敛为 `src.cli` 的兼容包装。
`build-bundle`、`experiments`、`serve` 分别委托发布脚本、实验 runner 和只读 API；
无子命令时只打印帮助，不训练、不写文件。保留模块化演示能力，但不再用一条“全流程”
脚本绕过 bundle。

**回归证据**：
[`test_usajobs_normalization_and_read_only_default_cli`](../tests/test_external_data_and_cli.py)
验证默认入口只展示帮助；完整门禁编译并格式化根入口。训练/服务一致性继续由 API
契约测试和 `ModelBundle` 校验保护。

**遗留边界**：CLI 目前是本地开发入口，没有任务队列、模型注册审批或发布回滚；这些
能力不应重新塞回入口函数。

### P-011：外部数据“能下载”不等于“能训练并对外宣称”

**问题与影响**：真实赛题数据丢失后，直接抓公开岗位、下载职业本体或寻找旧挑战数据
看似能补齐缺口，但这些来源的许可、粒度和实体空间不同。若没有来源版本、输入哈希、
用户 ID 处理和显式接入边界，很容易把受限数据提交到仓库，或把岗位文本导入误写成
真实推荐效果。

**分析思路**：先按用途拆分“职业/技能本体、岗位快照、用户画像、曝光交互”，逐项
核对官方获取方式与条款；再把获取、标准化、训练接入设为三个状态转换。只有每一步
都有契约和 lineage，才能判断失败发生在来源、映射还是模型协议。

**解决办法与取舍**：增加官方 USAJOBS API 获取示例，以及来源无关的 `ExternalJob`、
`ExternalInteraction` 和 manifest 契约。外部数据只写入被 Git 忽略的 staging；交互
必须使用环境变量密钥做 HMAC 伪名化，未知岗位引用和非法 schema 直接失败。staging
不会让训练或服务自动换源，避免未经评估的数据静默进入 bundle。

**回归证据**：
[`test_external_snapshot_validates_references_and_pseudonymizes_users`](../tests/test_external_data_and_cli.py)
验证原始用户 ID 不进入输出、输入哈希被记录、未知岗位被拒绝；同文件的 USAJOBS
fixture 验证官方响应到最小岗位契约的映射。来源与接入条件由
[数据与评估](data-and-evaluation.md#3-外部数据获取与隔离准备)维护。

**遗留边界**：当前没有 ESCO/O*NET 自动映射、简历授权采集、真实时间切分或外部数据
训练结果。伪名化也不是匿名化；许可、同意、删除和安全仍需独立治理。

### P-012：加密原语存在不等于 Data Privacy 条款完成

**问题与影响**：早期仓库有 AES-GCM 辅助函数和单字段篡改测试，但系统数据库没有
实际存储赛题点名的姓名、手机、邮箱、通讯地址四项密文，也没有授权解密 API。更严重
的是 admin、recruiter 和普通用户曾共用一个密码，角色仅由用户名决定；知道普通密码
即可请求管理员令牌。因此不能把“加密函数存在”写成赛题隐私要求已完成。

**分析思路**：回到赛题 PDF 第 3 页、印刷页码 71，把要求拆成“简历不泄露、数据库
至少四字段加密、只有授权人员解密”三个可观察条件。分别追踪明文从请求到数据库的
数据流、SQLite 实际字节、密文的用户/字段归属，以及 token 角色获取路径；不以
算法名称或接口 200 代替验收。

**解决办法与取舍**：增加 `EncryptedProfileStore`，在 SQLite 之前逐字段 AES-GCM
加密，随机 salt/nonce，经 PBKDF2 派生 key，并用 `user_id + field` 作为 AAD；API
只允许本人/admin 写、读、删。admin/recruiter/普通用户使用不同密码来源，recruiter
只获得反向匹配结果，不接触联系方式。简历文本保持请求级使用，不写入事件或档案库。

**回归证据**：
[`test_private_profile_store_encrypts_four_fields_and_binds_ciphertext`](../tests/test_security_persistence_and_statistics.py)
直接验证 SQLite 文件不含四项明文，并把合法姓名/邮箱密文调换后确认认证失败；
[`test_authenticated_api_known_cold_start_competency_and_feedback`](../tests/test_api_contract.py)
验证本人/admin 可读、其他用户/recruiter 返回 403、普通密码不能换取高权限令牌和
删除后返回 404。逐条验收结论见
[数据与评估](data-and-evaluation.md#23-赛题-data-privacy-验收矩阵)。

**遗留边界**：开发默认密码和主密钥只适合本机；尚无 OIDC、KMS/轮换、TLS 部署证据、
访问审计、同意/撤回、保留期限、备份清除、SQLite 安全擦除和独立安全评审。因此只能
说赛题演示条款已验证，不能宣称法规合规或生产安全。

## 4. 新问题的收录标准

只有同时满足以下条件的问题才加入本文：已经定位并关闭；能解释一个可复用的工程
决策；有代码、测试或产物证据；仍未覆盖的边界能够明确说明。尚未解决的问题进入
issue 或任务计划，不提前写成“解决方案”；纯格式调整、依赖升级流水账和 Git 提交
摘要不收录。
