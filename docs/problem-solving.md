# 关键问题与解决思路

本文只保留能够形成高质量推荐算法面试追问的问题，不记录修改流水账。

## 1. 全目录打分无法证明召回能力

- **问题/影响**：原系统把所有岗位直接交给融合排序，却使用“多路召回”表述，无法定位
  候选阶段丢失，也不能对应召回算法岗位。
- **分析**：模型分数与候选协议混在 API 中；小目录没有性能问题，但架构概念不完整。
- **解决**：定义统一候选证据，LightGCN、文本、技能和热度/新鲜度各取 Top-K，合并时
  保留来源、原始分数和路内排名；实验单独记录 Candidate Recall。
- **证据**：`test_multi_route_recall_and_learned_ranker_keep_auditable_evidence`；五种子
  `Candidate Recall@80 = 0.7109`。
- **剩余边界**：当前是精确 Top-K，没有 ANN 延迟和近似召回验证。

## 2. 离线先归一化、在线先屏蔽导致口径漂移

- **问题/影响**：旧实验对全目录做 Min-Max 后才屏蔽 seen，在线却先屏蔽。候选极值会
  改变归一化，使离线指标与在线分数不可直接对应。
- **分析**：请求级归一化依赖候选集合，因此 masking 顺序是模型语义的一部分。
- **解决**：实验和服务都先确定允许岗位，再使用共享特征构造和候选排序。
- **证据**：API 测试验证已知用户不返回训练岗位；协议测试验证 seen masking。
- **剩余边界**：Pointwise 使用全局训练标准化，不再依赖请求 Min-Max；Fusion 仅作为
  共享候选上的基线。

## 3. 模型版本没有覆盖排序和重排行为

- **问题/影响**：旧模型版本只包含数据和 LightGCN 权重，修改融合权重仍可能沿用旧
  版本，曝光归因会混淆不同在线行为。
- **分析**：推荐系统的 Serving 身份应覆盖所有改变最终顺序的配置，而不只是神经网络。
- **解决**：Bundle v3 新增 `serving_sha256`，覆盖数据、checkpoint、Pointwise 参数、
  文本配置和重排配置，模型版本由该哈希导出；Torch 保存时使用文件对象，避免随机临时
  文件名进入 ZIP archive，连续重建相同状态得到相同内容哈希。
- **证据**：`test_bundle_publish_has_content_identity`；连续两次相同 seed/epoch 发布得到
  同一版本 `jobrec-feed-07a2a9ac74aae85e`。
- **剩余边界**：演示目录仍由 seed 和源代码生成，不是独立 catalog snapshot。

## 4. 生成式兴趣不能成为无证据画像

- **问题/影响**：直接让 LLM 生成兴趣可能把不存在的技能写进召回 query，导致解释和
  推荐不可核对。
- **分析**：生成式模块适合扩展检索表达，但每个扩展项必须能回指简历或近期行为。
- **解决**：结构化 Schema 要求每个兴趣/query 都有输入证据；适配器失败、超时或校验
  不通过时整体降级为确定性技能词项提取。
- **证据**：`test_interest_expansion_only_uses_terms_with_input_evidence`。
- **剩余边界**：没有配置外部模型运行实验，生成效果标记为环境受限。

## 5. 学习排序没有超过固定融合

- **问题/影响**：Pointwise Recall@10 为 0.1410，低于 Fusion 的 0.2551，无法支持
  “学习排序提升效果”的叙述。
- **分析**：每种子约 1.5k 训练曝光、约 10% 正例，且特征是训练窗口末端快照；技能
  Fusion 又与生成分布机制高度一致。
- **解决**：保留 Pointwise 作为曝光学习和发布链路，完整报告负面结果；不调生成器或
  删除简单基线来制造提升。
- **证据**：`uv run python main.py experiments` 和机器可读五种子结果。
- **剩余边界**：真实改进需要 point-in-time 特征、更长序列、验证集和真实目标标签。
